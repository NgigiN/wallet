# Wallet v2 — multi-user platform design

Status: approved by user 2026-09-11 (same-origin hostname; Postgres container).
Date: 2026-09-11
Author: drafted with Claude from the 2026-09-11 brainstorm.
Progress tracker: `docs/superpowers/PROGRESS.md` (living document, updated per stage).

## 1. Goal

Turn the single-user wallet (Go API + Discord bot + Android SMS capture app,
one shared bearer token, one SQLite file) into a small multi-user product that
friends and family can use safely. Concretely:

- Anyone can create an account and use the app on Android, on iPhone, and on a
  laptop, with all their devices showing the same data.
- A user can define their own categories, budgets, and auto-tag rules.
- A user can invite a partner into a shared space where both see and tag the
  same transactions.
- Mis-tagged transactions can be corrected from any device, and the correction
  propagates everywhere.
- Transactions from sources the parser does not know (banks, cash) can still be
  recorded.
- The service survives a server failure without losing data, and the user's
  existing history is carried over intact.
- The Discord bot is retired.

## 2. Decisions already made

These were settled in the brainstorm. They are recorded here so the spec does
not re-open them. Anything else in this document is open to review.

| Decision | Choice | Why |
|---|---|---|
| Backend stack | TypeScript: Hono on Node 22, BetterAuth, Drizzle ORM, PostgreSQL 16 | User named BetterAuth. It is TypeScript-only, so the Go backend is replaced rather than bridged. The Go code is ~1.8k lines; rewriting is cheaper than running two runtimes. |
| iOS strategy | No native iOS app. The web app is a PWA installed from Safari ("Add to Home Screen"). | iOS cannot read SMS regardless, so a native app buys nothing. A PWA needs no sideloading, no Mac, no App Store. Capacitor wrap is the upgrade path if an App Store listing is ever wanted. |
| Laptop dashboard | Same PWA, responsive layout. | One web codebase for iOS, desktop, and any Android user without the native app. |
| Android | Native app stays, for SMS capture only. Gains login and sync v2. | The only surface that can capture M-PESA/Airtel SMS automatically. |
| Distribution | Sideloaded APK and installed PWA for friends and family. No Play Store this cycle. | Avoids the Play SMS-permission review for now. Revisit in Phase 4. |
| Shared data model | Every transaction belongs to a **space**. Personal use is a one-member space. A couple is a two-member space. | Couples become an invite flow, not a schema change. |
| Space implementation | BetterAuth `organization` plugin. "Space" is the product name for an organization. | Gives members, roles, and email invitations without hand-rolled code. |
| Sync model | Server is source of truth. Changelog sync with a server-assigned sequence cursor. Clients are local-first and push dirty rows. | Solves multi-device, shared spaces, and re-tagging with one mechanism. |
| Money representation | Integer minor units (`amount_cents bigint`) in DB and API. | Exact arithmetic, no float drift in totals. |
| Identifiers | UUIDv7 generated by the client for transactions, so rows can be created offline and pushed idempotently. | Offline-first on web and Android. |
| Hosting | Same Contabo VPS. Postgres and the API run in Docker via `docker compose`. Host nginx keeps proxying `127.0.0.1:8080`. | No new infrastructure. Compose is fine here because the new stack is created by compose from day one (the old container was not; see memory notes). |
| Backups | Nightly `pg_dump`, encrypted with `age`, copied off-site with `rclone`. 30-day retention. Restore drill once per phase. | Durability matters more than uptime for a local-first app. |
| Branching | `main` is protected and always deployable. Long-lived integration branch `v2` for the rebuild. Feature branches PR into `v2`. `v2` merges to `main` at cutover. Deploy on version tags, not on every push. | Production is live and must keep working while the rebuild happens. |
| Discord | Deleted in Phase 1 at cutover. | User decision. Weekly/monthly reviews move to the web app. |
| Email provider | Resend (user to create account, verify `samtama.lol` sender). Until then, email + password login. | Magic-link and OTP login need a sending domain. Password login needs nothing. |
| Push | Firebase Cloud Messaging for Android and web (including installed iOS PWAs on iOS 16.4+). | User already plans a Firebase project. |
| Error tracking | Sentry (free tier) on server, web, and Android. | One place for crashes on all three surfaces. |
| Currency | KES only. Amounts formatted as `Ksh`. | All sources are Kenyan. Multi-currency is out of scope. |

Note on "BetterAuth logins": BetterAuth is a library, not a hosted service.
There is nothing to sign up for. The external accounts actually needed are
listed in section 19.

## 3. Non-goals (explicit backlog)

- Play Store or App Store listing.
- End-to-end encryption of transaction data (conflicts with shared spaces and
  server-side stats; see 15.5 for what is done instead).
- Multi-currency.
- Statement import (M-PESA PDF/CSV, bank CSV). Design hook only (section 14).
- LLM-based parsing of unknown SMS formats. Design hook only.
- Web-based SMS capture. Impossible; manual entry is the iOS/laptop path.
- Multiple spaces per user beyond personal + shared. The schema allows it; the
  UI exposes at most one shared space per user this cycle.
- Staging environment beyond a second compose project on the same VPS.

## 5. Data model

All tables live in one Postgres database. Drizzle owns the schema;
`drizzle-kit generate` produces SQL migrations committed under
`server/drizzle/` and applied on container start with `drizzle-kit migrate`.

### 5.1 Owned by BetterAuth

`user`, `session`, `account`, `verification` (core) and `organization`,
`member`, `invitation` (organization plugin). Column names are the plugin
defaults. We never write to these directly except through BetterAuth APIs.

Product vocabulary → plugin tables:

| Product term | Table | Notes |
|---|---|---|
| Space | `organization` | `slug` is a generated UUID; `name` is user-visible. `metadata` JSON holds `{ "kind": "personal" \| "shared" }`. |
| Membership | `member` | Roles: `owner`, `member`. |
| Invite | `invitation` | Email invites with expiry; accepted through the BetterAuth flow. |

A personal space is created for every new user by a `databaseHooks.user.create.after`
hook. It cannot be left or deleted except through account deletion.

### 5.2 Application tables

Every application table that syncs carries the same four columns:

| Column | Type | Meaning |
|---|---|---|
| `seq` | `bigint not null` | Global change sequence, `nextval('change_seq')`, reassigned on **every** write. Sync cursor. |
| `created_at` | `timestamptz not null default now()` | |
| `updated_at` | `timestamptz not null default now()` | Server clock, set on every write. |
| `deleted_at` | `timestamptz null` | Soft delete. Rows are never hard-deleted while any client might hold a cursor older than the delete. A weekly job hard-deletes tombstones older than 90 days. |

`change_seq` is a single global Postgres sequence shared by all syncing tables.
Sync clients only ever compare `seq` values, so a single sequence keeps the
cursor total-ordered across tables.

| Column | Type | Notes |
|---|---|---|
| `space_id` | `text pk fk organization.id` | |

| `week_starts_on` | `smallint not null default 1` | ISO Monday. |

| `emoji` | `text not null` | Single grapheme. |

Seed on space creation (matches the current app): food, travel, savings,

**`transactions`**

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid pk` | Client-generated UUIDv7. |
| `space_id` | `text fk` | |
| `captured_by` | `text fk user.id` | The member whose device produced the row. |
| `source` | `text not null` | `mpesa` \| `airtel` \| `manual` \| `bank:<code>` (Phase 4). |
| `receipt_code` | `text null` | Provider receipt (e.g. `TID60759AQ`). Null for `manual`. |
| `direction` | `text not null` | `in` \| `out` \| `transfer`. |
| `amount_cents` | `bigint not null` | > 0. |
| `cost_cents` | `bigint not null default 0` | Provider fee. |
| `balance_cents` | `bigint null` | Post-transaction balance if the SMS carried one. |
| `counterparty` | `text not null` | Cleaned name/agent/till. |
| `occurred_at` | `timestamptz not null` | From the SMS, parsed in the phone's zone. |
| `category_id` | `uuid null fk categories.id` | Null = untagged. |
| `reason` | `text null` | |
| `linked_transaction_id` | `uuid null fk transactions.id` | The other half of a partner-to-partner transfer (section 8.3). |
| `client_updated_at` | `timestamptz not null` | Client's wall clock at its last edit. Used for last-writer-wins on tag fields. |
| sync columns | | |

Constraints:

- `unique (space_id, source, receipt_code, direction) where receipt_code is not null`.
  This is the dedupe key. Including `direction` is what lets both halves of a
  transfer between two members of one space coexist (both phones see the same
  receipt code, one as `out`, one as `in`).
- `check (amount_cents > 0)`, `check (direction in (...))`.
- Index `(space_id, seq)` for sync pulls; `(space_id, occurred_at desc)` for
  lists; `(space_id, category_id, occurred_at)` for stats.

Raw SMS bodies are **not** stored on the server. The Android app keeps
`raw_body` locally for re-parsing and debugging only.

Only populated when the user explicitly taps "Report this format".

### 5.3 Authorization rule

Every application query is scoped by `space_id`, and a request may only touch
a space where `member(user_id, space_id)` exists. This is enforced once in a
Hono middleware that resolves `:spaceId` from the path, checks membership,
and attaches `{ user, space, role }` to the context. Handlers never take a
`space_id` from the request body.

## 6. Authentication and identity

- BetterAuth configured with the Drizzle adapter (`provider: "pg"`).
- Methods:
  - Phase 1: email + password (`emailAndPassword.enabled`), minimum 10
    characters, scrypt hashing (BetterAuth default). Email verification off
    until Resend exists, then turned on for new sign-ups.
  - Phase 2, once Resend is configured: `emailOTP` plugin as the primary login
    for the web PWA (six-digit code), password kept as fallback.
- Sessions:
  - Web: HttpOnly, Secure, SameSite=Lax cookie. 30-day expiry, refreshed on use.
  - Android: `bearer` plugin. The app reads the `set-auth-token` response header
    at sign-in, stores it in `EncryptedSharedPreferences`, and sends
    `Authorization: Bearer <token>` on every request.
- Rate limiting on `/api/auth/*`: 10 requests per minute per IP, in-memory
  (single process). Returns 429.
- CORS: only `https://wallet.samtama.lol` (and `http://localhost:5173` in dev).
- Account deletion: `DELETE /api/v2/me` requires the password (or a fresh OTP).
  Removes the user, their personal space and all its rows, their memberships,
  and their devices. Shared-space rows they captured remain, re-attributed to
  `captured_by = null`, because the partner still owns that history.
- Data export: `GET /api/v2/spaces/:id/export?format=json|csv` streams all
  non-deleted transactions with category names resolved.

## 7. Sync protocol v2

Local-first: both clients keep a full copy of their spaces and work offline.
The server is authoritative; `seq` is the cursor.

### 7.1 Pull

```
GET /api/v2/spaces/:spaceId/sync?since=<seq>&limit=500
→ 200 {
    "cursor": <max seq in this page>,
    "more": true|false,
    "transactions": [ ...rows incl. deleted_at ... ],
    "categories":   [ ... ],
    "budgets":      [ ... ],
    "rules":        [ ... ]
  }
```

Rows from all four tables with `seq > since`, ordered by `seq`, paged
together so the cursor is consistent. Tombstones are included so clients can
delete locally. The client stores `cursor` per space and loops while `more`.
First sync uses `since=0`.

### 7.2 Push

```
POST /api/v2/spaces/:spaceId/sync
{
  "transactions": [ { full row, "client_updated_at": ... } ],
  "categories":   [ ... ],
  "budgets":      [ ... ],
  "rules":        [ ... ]
}
→ 200 {
    "results": [ { "table": "transactions", "id": "...", "status": "applied"|"unchanged"|"rejected", "error"?: "...", "row"?: {...} } ],
    "cursor": <seq after applying>
  }
```

Semantics, applied inside one Postgres transaction per request:

- **Create**: row id unknown → insert. If the dedupe key already matches an
  existing row (same receipt code and direction from another device), the push
  is treated as an edit of that row and the client gets `row` back so it can
  replace its local id. This is what makes two phones capturing the same SMS
  converge.
- **Edit of immutable fields** (`source`, `receipt_code`, `direction`,
  `amount_cents`, `cost_cents`, `balance_cents`, `occurred_at`) on a
  non-`manual` row → `rejected` with error `immutable`. `manual` rows may edit
  amount, counterparty, and `occurred_at`.
- **Edit of tag fields** (`category_id`, `reason`, and for manual rows the
  fields above): last-writer-wins by comparing incoming `client_updated_at`
  with the stored `client_updated_at`. Older wins nothing and returns
  `unchanged` with the current `row`.
- **Delete**: `deleted_at` set → soft delete, subject to the same LWW rule.
- Every applied write gets a new `seq` and server `updated_at`.
- Category references must exist in the same space and not be deleted, else
  `rejected` with `bad_category`.

Clients mark rows dirty on any local edit, push dirty rows, then pull. The
pull after a push returns the client's own writes; clients apply them
idempotently (same id, same content).

### 7.3 Client state machine (both clients)

Local rows have `sync_state`: `dirty` | `clean` | `error`. Any local edit sets
`dirty`. A successful push sets `clean`. `rejected` sets `error` with the
message shown in the row's detail view, and is retried only after the user
edits again. This replaces the current `UNTAGGED/TAGGED/SYNCED` states on
Android; `UNTAGGED` becomes "clean with null category" and `PARSE_FAILED`
stays as a local-only state for rows that never got a valid parse.

### 7.4 Versioning

Every request carries `X-Client: android/1.2.0` or `X-Client: web/1.2.0`.
The server holds `MIN_CLIENT_VERSION` per platform in env. Older clients get
`426 Upgrade Required` with `{ "error": "upgrade_required", "min": "1.2.0" }`
on every `/api/v2/*` route. Both clients show a blocking "update needed"
screen on 426. This exists from the first v2 release so the protocol can
change later without corrupting data.

## 8. Transaction lifecycle

### 8.1 Capture (Android)

Unchanged in spirit: SMS arrives, parser produces a row, heads-up notification
offers the two most-used categories, tag screen for the rest. Changes:

- The row is created locally with a UUIDv7 and `sync_state = dirty`
  immediately, even before tagging, so an untagged transaction reaches other
  devices and the partner can tag it.
- Auto-tag rules (Phase 2) are applied locally at capture time if a matching
  rule exists; the notification then says "Tagged as Food (rule)" with an
  "Change" action.

### 8.2 Manual entry (web and Android)

Amount, direction, counterparty, date/time, category, reason. `source =
manual`, `receipt_code = null`. Fully editable later.

### 8.3 Partner transfer detection (Phase 3)

On push, when a transaction with `direction = in` and receipt code `R` lands
in space `S`, and `S` already holds a row with the same `R`, `direction =
out`, captured by a different member: link both rows via
`linked_transaction_id`, and set both to the space's system `transfer`
category if they are untagged. Stats exclude linked pairs from spend and
income so money moving between partners is not counted as either. The same
rule runs in the opposite order when `out` arrives second.

### 8.4 Re-tagging and bulk re-tag (Phase 2)

Any member can change category/reason on any row in the space from any
device; sync v2 propagates it. Bulk re-tag: "Tag all from <counterparty> as
<category>" applies to every untagged or same-category row with that
normalised counterparty in the space, and offers to create a rule.

### 8.5 Rules (Phase 2)

Applied client-side at capture (Android) and server-side on push for rows
that arrive untagged from a client that has not yet synced the rule. Manual
tags always win over rules; a rule never overwrites a non-null category.

## 9. Web PWA (`web/`)

- Vite, React 19, TypeScript, React Router, TanStack Query for server state,
  Dexie (IndexedDB) for the local copy, `vite-plugin-pwa` for manifest and
  service worker (precache the app shell, network-first for `/api`).
- Design: reuse the Android "canopy" tokens (emerald palette, Sora font,
  category colours/emoji) so the two surfaces feel like one product.
  Mobile-first with a bottom tab bar; on ≥ 900 px the tab bar becomes a left
  rail and lists get a detail pane.
- Installability: manifest with `display: standalone`, maskable icons, iOS
  meta tags, safe-area insets, `100dvh` layouts, no tap highlight. An
  "Install" hint appears once on iOS Safari explaining Share → Add to Home
  Screen.
- Offline: opens instantly from cache, shows local data, queues edits, syncs
  when online. Login is required online once; the session cookie persists.
- Screens (Phase 1B unless marked):
  1. Sign in / sign up (email + password; OTP in Phase 2).
  2. Inbox: untagged first, then recent. Tap to tag. Swipe/long-press for
     re-tag and delete.
  3. Add transaction (manual).
  4. Stats: totals, category breakdown with budget bars, period navigation
     (week/month/year with jump), comparison to previous period. Review tab
     with trend strip, movers, pace, heatmap (ports the Android
     `ReviewSection`).
  5. Categories: list, add, edit (name/emoji/colour), archive, reorder.
  6. Budgets: per-category monthly limit.
  7. Settings: profile, devices, export, delete account, install hint.
  8. Space (Phase 3): members, invite partner, accept invite, leave.
  9. Rules (Phase 2): list, add, delete; "created from bulk re-tag".
- Amount masking: header totals hidden by default with an eye toggle, same
  as Android (user's explicit preference; not persisted).

## 10. Android app changes (`android/`)

Phase 1D, after the backend and web are live and the user's own data is
imported.

- **Login screen** replaces the URL/token settings. Base URL is a build
  config constant (`https://wallet.samtama.lol`), overridable in debug builds.
- **Session**: bearer token in `EncryptedSharedPreferences`. 401 → sign-out
  and back to login. 426 → blocking upgrade screen.
- **Room migration 2 → 3**:
  - `transactions`: add `uuid` (server id), `space_id`, `category_id`,
    `sync_state`, `client_updated_at`, `server_seq`; keep `category` name
    column during migration, backfill `category_id` from the synced
    categories table on first sync, then drop in migration 3 → 4 one release
    later.
  - New tables `categories`, `rules`; `budgets` gets `category_id`. The local
    alert-state columns stay until Phase 3 (D3.5) removes local alerting.
  - Amounts stay `Double` in Room for now; the sync layer converts to/from
    cents at the wire boundary with rounding to the nearest cent.
- **Sync v2 client** in `sync/`: replaces `Sync.pushAll` + `Hydrate.pull`
  with push-dirty-then-pull-cursor. Pull-to-refresh and periodic worker
  unchanged in cadence.
- **Category picker** reads from the local `categories` table, ordered by
  `sort_order`, excluding archived. Colours/emoji come from the row; the
  hard-coded maps become fallbacks only.
- **Budgets** read from the synced table; local alert logic removed in favour
  of server push (Phase 3). Between 1D and Phase 3, alerts are computed
  locally as today but from synced budgets.
- **Devices**: register on login with FCM token (Phase 3).
- Unit tests updated for the new state machine and wire conversion; CI runs
  `./gradlew testDebugUnitTest`.

- Sentry on unhandled errors, tagged with user id and space id only.
- Graceful shutdown on SIGTERM; migrations run before the server listens.
- Env: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `RESEND_API_KEY`
  (optional), `FCM_SERVICE_ACCOUNT_JSON` (optional), `SENTRY_DSN` (optional),
  `LEGACY_API_TOKEN` + `LEGACY_SPACE_ID` (Phase 1C only), `MIN_CLIENT_ANDROID`,
  `MIN_CLIENT_WEB`.

### 11.4 Version policy

`MIN_CLIENT_*` bumps are a deliberate release step, listed in the release
checklist in `PROGRESS.md`. A bump is only made after the new client build has
been in the user's hands for at least a week.

## 12. Migration and cutover

### 12.1 Legacy compatibility shim (Phase 1C)

The current Android app keeps working during Phase 1C–1D without any change:

- `POST /api/transactions` with `Authorization: Bearer $LEGACY_API_TOKEN`
  maps the old JSON to a v2 row in `LEGACY_SPACE_ID` (the user's personal
  space), `captured_by` = the user's id, category resolved by name (created
  if missing, as `expense`). Returns `201`/`200` exactly as before.
- `GET /api/transactions` returns the old shape for that space.
- Removed in the Phase 1D PR that ships the Android login build, after the
  user confirms the new build is installed.

### 12.2 Import script (`server/scripts/import-sqlite.ts`)

Input: a copy of `transaction.db` and the user's email. Steps:

1. Ensure the user exists (create with a random password if not; user
   resets), ensure the personal space exists.
2. Seed the seven categories if absent.
3. For every row in SQLite `transactions` (`deleted_at is null`):
   - `source` empty → `mpesa`; `direction` empty → `out` (matches current
     API behaviour).
   - `category` name → `category_id` by case-insensitive lookup; unknown
     names create an `expense` category with a neutral colour; empty or
     `uncategorized` → null.
   - `amount`, `cost`, `balance` → cents with round-half-up.
   - `receipt_code = transaction_id`; `id` = deterministic UUIDv5 of
     `(space_id, transaction_id, direction)` so re-runs upsert.
   - `client_updated_at = updated_at` from SQLite.
4. Print counts: read, inserted, updated, skipped-duplicate, unknown
   categories created, with the sum of `amount_cents` by direction to compare
   against `SELECT direction, SUM(amount) FROM transactions` on the source.
5. Wrapped in one Postgres transaction; any error rolls back everything.

Acceptance: row count and per-direction sums match the SQLite source
exactly; the web Stats for the current and previous month match the Android
Stats screen for the same periods.

### 12.3 Cutover runbook (Phase 1C)

1. `sqlite3 transaction.db ".backup"` on the VPS; copy to local machine and
   to the backup bucket. Verify row count.
2. `docker compose -p wallet2 up -d postgres`; run migrations; run the import
   script against the copy; verify counts.
3. Start `api` on port `8081`, smoke-test `/health`, login, pull.
4. Stop `financial-tracker-bot`. Re-point compose `api` to `8080`, restart.
   nginx untouched.
5. Smoke: `/health` through Cloudflare; the Android app's pull-to-refresh
   succeeds through the legacy shim; a fresh SMS on the phone syncs and
   appears in the web inbox.
6. Discord bot token revoked in the Discord developer portal.
7. Old container and `data/transaction.db` kept for 14 days, then removed.

Rollback at any step before 6: `docker start financial-tracker-bot` on 8080.

## 13. Notifications (Phase 3)

- `firebase-admin` on the server with the service account JSON from env.
- Android: FCM SDK, token registered via `POST /api/v2/me/devices`.
- Web: FCM JS SDK with a VAPID key; works in Chrome/Edge/Firefox and in
  installed PWAs on iOS 16.4+ (not in a plain Safari tab).
- Budget alerts: after every push that changes an `out` transaction, the
  server recomputes month-to-date spend for the affected categories in the
  space's timezone and, if a budget crosses 80% or 100% and `budget_alerts`
  has no record for that `(category, month, level)`, sends to every device of
  every member and records it.
- Partner activity (optional toggle): "Partner tagged 3 transactions".
- Daily "you have N untagged" reminder moves from the Android worker to a
  server job at 20:00 space time, sent only to devices with the toggle on.

## 14. Unknown sources (Phase 4)

- Android `SmsParser` becomes a registry keyed by sender id
  (`mpesa`, `airtelmoney`, then bank sender ids as samples arrive). Each entry
  has a list of regex templates and a test file with real redacted samples.
- Receiver accepts any sender in the registry. Money-shaped messages from
  unknown senders (amount pattern + `Ksh`/`KES`) go to `PARSE_FAILED` with the
  existing manual-completion flow.
- "Report this format" on a `PARSE_FAILED` row sends the sender id and a
  redacted body (digits runs longer than 4 replaced by `#`, names left as-is
  after user confirmation) to `POST /api/v2/unrecognised-sms`. The user of the
  system (you) reviews these and adds templates.
- Design hook, not built: a server-side LLM extraction fallback for reported
  formats, and statement import.

### 15.1 Deploy

- `deploy/compose.yml`: services `postgres` (16-alpine, volume `pgdata`,
  healthcheck), `api` (built from `server/Dockerfile`, multi-stage, Node 22
  alpine, `web/dist` copied in at build), `backup` (alpine cron sidecar

  `127.0.0.1:8080`.
- Secrets in `/home/deploy/opt/wallet/.env`, referenced by compose

  this and is removed).
- Deploy workflow: on tag `v*`, SSH to VPS, `git fetch && git checkout <tag>`,
  `docker compose -p wallet2 up -d --build`, wait for `/health`, fail the
  job on non-200. Manual `workflow_dispatch` allowed for the same steps.
- Staging: `docker compose -p wallet2-staging -f deploy/compose.yml -f deploy/compose.staging.yml up`
  on port `8082`, `staging.wallet.samtama.lol` vhost (one-time nginx edit
  with the user's sudo). Used to rehearse cutover and migrations.

### 15.2 Backups

- `deploy/backup.sh`: `pg_dump -Fc` → `age -r <public key>` → `rclone copy`
  to the bucket, name `wallet-YYYYMMDD-HHMM.dump.age`. Runs 02:00 daily.
  Retention 30 daily + 6 monthly via `rclone delete --min-age`.
- Restore drill `deploy/restore.md`: pull latest dump, `age -d`,
  `pg_restore` into a scratch database, run three count queries, compare with
  production. Performed and recorded in `PROGRESS.md` at the end of every
  phase.
- Pre-cutover: the SQLite file is backed up to the same bucket (Phase 0).

### 15.3 Migrations

Drizzle-generated SQL in `server/drizzle/` committed with each PR that changes
the schema. Applied on `api` start. Every migration is rehearsed on staging
against a restored production dump before the tag is cut. Remove
`migrations/` from `.gitignore` in Phase 0 (it would swallow the directory).

### 15.4 Observability

- `/health` returns `{status, db: ok|fail, version, uptime}`; 503 on db fail.
- Uptime Kuma, already running on the VPS at `status.samtama.lol`, monitors
  `/health` every 5 min, alerting to the user's email.
- Sentry DSNs for server, web, and Android.
- `docker compose logs` is the log store for now; no external log shipping.

### 15.5 Security

- TLS at nginx (existing), HSTS already set by Cloudflare.
- Cookies HttpOnly/Secure/SameSite=Lax; bearer tokens only from the Android
  app; CORS locked to the origin.
- Postgres reachable only on the compose network. Password in `.env`.
- Raw SMS bodies never leave the phone (section 5.2). Counterparty names and
  balances are stored; that is the minimum the product needs.
- VPS disk: confirm LUKS or provider encryption is on; if not, note the gap.
  Backups are encrypted with `age` regardless.
- Auth rate limits (section 6). Sync endpoints limited to 60 requests/min per
  user.
- Dependencies pinned; `npm audit` and `gradle` dependency checks in CI as
  warnings.

### 15.6 CI and branching

- Branch protection on `main` and `v2`: PR required, CI green required, no
  force-push.
- `ci.yml` on every PR: server `vitest` + typecheck; web typecheck + build;
  Android `./gradlew testDebugUnitTest`; Go tests while Go still exists.
- `deploy.yml` on tag `v*` only (section 15.1). The existing push-to-main
  deploy is removed in Phase 0.
- Android release builds signed with a keystore stored as a GitHub secret;
  `release.yml` on tag attaches the APK to a GitHub Release so friends have
  one download link.

## 17. Testing strategy

Every phase ships with tests at three levels; the progress tracker lists the
exact commands per stage.

- **Unit** (fast, no I/O): sync merge rules, LWW, dedupe-as-edit, partner
  transfer linking, rule matching, cents conversion, import mapping, period
  math, budget alert thresholds. Server: `vitest`. Web: `vitest`. Android:
  JUnit as today.
- **Integration** (Postgres in Docker, `testcontainers` or a compose
  service): auth flows, membership enforcement (a member of space A cannot
  read space B: must be a test), sync pull/push round trips, legacy shim,
  import script against a fixture SQLite built from real redacted rows.
- **End-to-end**: Playwright against the web app on a local stack: sign up,
  add manual transaction, tag, see it in stats, offline edit then reconnect.
  Android: instrumented smoke test on the user's device for capture → sync →
  web visibility, recorded manually in the tracker.
- **Migration rehearsal**: every schema change applied to a restored
  production dump on staging before tagging.
- **Data parity gate** for cutover: counts and sums (section 12.2).

## 20. Risks and open questions

- **BetterAuth organization plugin fit.** If its invitation flow proves awkward
  for a two-person "partner" model, the fallback is our own `spaces`/`members`
  tables with the same product behaviour. Decide during D1A.1; the rest of the
  spec is unaffected.
- **Room migration on the user's live phone.** Rehearse on a debug build with a
  copy of the real database before the release build.
- **Cents rounding of legacy floats.** Round-half-up on import; the parity gate
  will surface any drift.
- **Partner transfer edge case.** If both partners' phones capture the same
  receipt with the same direction (e.g. both receive a group payout), the
  dedupe treats it as one row. Acceptable; noted.
- **iOS PWA push** only works when installed to the home screen. The install
  hint must be prominent.
- **VPS single point of failure.** Accepted; backups plus a documented
  rebuild from compose keep recovery under an hour.
